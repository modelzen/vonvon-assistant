# Vonvon Bot 问题与功能反馈（提交高质量 Issue 或复现评论）

本 Skill 负责把用户的排查结论或产品想法，打磨成**查过重、质量过关、默认带图、严格脱敏、符合官方模板**的 GitHub Issue（或对已有 Issue 的高质量补充评论）。**全程由 Bot 主动把关与引导，用户只需回答少量关键追问并在预览时确认即可。**

## 第零步：初始化闸门（必检，不可跳过）

开始起草或提交任何反馈前，必须先检查 `workspace/setup-state.json` 是否存在：
- **如果不存在**：先简短承接用户要反馈的问题（说明已记下要点，不用重复发），立即转入 `vonvon-setup`——在同一轮里做完只读体检并给出 A / B 档位选项，初始化完立刻无缝回到这里继续起草。仅在用户明确回复「本次先跳过」时才直接继续。
- **如果已存在**：从 `workspace/setup-state.json` 读取 `upstreamRepo`（默认 `modelzen/vonvon-bot`）、`repoPath`、`assistantRepoUrl` 与 `ghReady`，继续第一步。

## 第一步：安全漏洞闸门（最先检查）

如果用户反馈的问题涉及**安全漏洞**（如密钥/凭据泄露、沙箱逃逸、未授权访问、命令注入、提权等）：
- **立即停止公开提 Issue 或评论**；
- 告知用户不要公开发布细节，并指引查阅 `https://github.com/modelzen/vonvon-bot/blob/main/SECURITY.md` 走私下安全报告渠道。

## 第二步：先查重，判断「新建 Issue」还是「给已有 Issue 补发复现评论」

在起草前，先搜索 `<upstreamRepo>` 是否已有相同或高度相关的 Issue（包括 open 和近期 closed）：
- 已登录 `gh` 时：
  ```bash
  gh issue list --repo <upstreamRepo> --state all --search "<核心关键词>" --limit 10
  ```
- 未装 `gh` 但可联网时：搜索 `https://github.com/modelzen/vonvon-bot/issues`。
- 若是 Bug 且本地仓库可读，同时核对上游 `dev` 是否已修复。

**命中已有 Open Issue 时**：
- 把已有 Issue 编号、标题、链接展示给用户，并主动说明建议：**「直接往 `#<编号>` 补充你这次的环境、脱敏报错和现场截图，比另开重复 Issue 更能帮维护者定位」**（若用户确认场景明显不同，再新建 Issue）。
- **重要**：给已有 Issue 补发复现评论时，**同样执行下面第三步～第五步的全部标准**（质量自检、默认保留并裁剪脱敏话题截图、统一带来源署名、预览确认后再发布）。

## 第三步：主动质量把关 + 默认保留截图（不要等用户反问才优化！）

先自动复用当前话题（尤其是 `vonvon-diagnose` / `vonvon-qa`）已查明的全部上下文，**不让用户重复填写已知信息**。

### 1. 出预览前先做一轮「维护者视角质量自检」

不要把半成品草稿丢给用户，等用户反问「符不符合要求、要不要优化」——Bot 自己先过一遍清单，能从上下文和源码补齐的直接补齐，确实缺关键决策点时用 **1～2 个简短选择题**主动向用户确认：

- **类型 A：Bug 报告（对齐 `.github/ISSUE_TEMPLATE/bug.yml`）或复现评论**
  1. **Vonvon Bot 版本**（如 `0.10.1`）
  2. **运行环境**（OS、CPU 架构、模型工具 Codex / Claude 及版本；远程连接时写明两端系统）
  3. **最小复现步骤**（按编号写清从哪开始、开了哪些开关、怎么触发）
  4. **预期与实际结果**（对照写清预期行为 vs 实际异常）
  5. **精简脱敏日志 + 源码定位 + 现象截图/短录屏**（附关键报错码/行号和定位到的源码链接，维护者一眼就能看懂）
- **类型 B：功能建议 / 体验优化（对齐 `.github/ISSUE_TEMPLATE/feature.yml`）**
  1. **你想完成什么**（真实痛点场景、触发频率、当前哪里卡壳；如能定位对应现状源码一并附上链接）
  2. **你希望 Vonvon Bot 怎么做**（不只写泛泛想法，**主动帮用户理清关键触发边界/拆分规则**，并**主动补上 1～2 个具体可验证的「验收例子」**，让维护者一看就懂预期效果；有临时替代做法也一并写明）

### 2. 默认保留话题截图 + 尽量提倡带图/录屏（新建与补评一视同仁）

- **话题里用户已经发过现象截图或录屏**：**必须默认保留它**！主动裁剪到只保留说明问题所需的最小局部区域（例如报错行、异常卡片区域，裁掉无关群名/昵称/聊天上下文），保存到 `workspace/feedback-media/` 并连同文字草稿一起预览——**绝不要擅自丢弃用户已发的截图改写成纯文字版！**
- **话题里还没有图，但问题涉及界面、卡片展示、弹窗或交互**：在出草稿时主动轻提一句：「如果你方便顺手截一张图或录 10 秒短片发给我，我帮你裁好脱敏一起附上去，维护者能一眼看懂；不方便的话直接回 **确认提交** 也可以。」

### 3. 统一来源标识（新建 Issue 与补发评论都附在末尾）

在公开正文末尾追加一行克制的来源署名（绝不夹带本机路径、Bot 名、飞书 ID 等任何隐私字段）：

```markdown
---
<sub>通过 vonvon-assistant（`vonvon-feedback`）辅助排查与整理</sub>
```

- 如果 `workspace/setup-state.json` 已配置非空的公开 `assistantRepoUrl`，将 `vonvon-assistant` 写成 `[vonvon-assistant](<assistantRepoUrl>)`；
- 走无 `gh` 网页表单时，附在表单最后一块内容末尾；
- 预览时明示给用户；如果用户明确要求去掉则尊重去掉。

## 第四步：强制脱敏审查 + 文字与媒体完整预览确认（绝不可跳过）

在执行任何公开提交动作前，**逐行审计草稿并完成脱敏**：

- 删除或替换所有 API Key、App Secret、Bearer Token、Cookie、私钥；
- 将飞书应用 ID（`cli_...`）、用户 ID（`ou_...`）、群 ID（`oc_...`）替换为 `<app_id>` / `<open_id>` / `<chat_id>`；
- 删除私有飞书云文档/群链接、内部域名、私有 IP、以及暴露本机真实用户名或私有项目名的绝对路径（用 `~/` 或 `<workspace>` 替代）；
- 日志只保留与问题直接相关的关键行，不倾倒整份日志；
- **图片与视频预览及打码提醒**：若附带任何截图或录屏，**必须把裁剪/处理后的图片或视频直接发到群里让用户预览**，明确提醒检查画面里是否还残留敏感信息（私密群聊、人名/头像、Token、地址栏凭据、私人目录名、无关标签页等）；需要打码或重裁时先改好再预览。

然后展示**完整的类型（新建 Bug / 新建功能建议 / 评论 `#<编号>`）、标题、脱敏正文与全部媒体预览**，并用清晰短选项结尾：
> 「请核对上面的文字脱敏和截图画面（如还有要打码的地方直接告诉我）。没问题回复 **确认提交** 我就发布；想修改某处或补充截图直接说就行。」

**未收到用户明确确认，绝不执行提交。**

## 第五步：提交发布与结果核验（支持无 `gh` 优雅兜底）

收到用户确认后，按本机环境自动选路：

### 路径 1：已安装且登录 `gh`（命令行直提）

1. 将正文写入 `workspace/.issue-draft.md`（保留草稿直到确认发布成功，避免中途异常退出时要重头来过）：
   - **新建 Issue**：
     ```bash
     gh issue create \
       --repo <upstreamRepo> \
       --title "<标题>" \
       --body-file workspace/.issue-draft.md
     ```
   - **给已有 Issue 补发复现评论**：
     ```bash
     gh issue comment <编号> \
       --repo <upstreamRepo> \
       --body-file workspace/.issue-draft.md
     ```
   （不强行传无权限的 `--label` 导致创建失败。）
2. **媒体附件处理与核验**：
   - 若通过可上传图片的流程把截图/录屏一并发布了，发完后核对目标链接与图片正常显示再回复用户；
   - 若仅通过纯 `gh` 命令提交（无法直接上传本地二进制图/视频），把创建成功的 **Issue / 评论链接** 与已确认脱敏的本地媒体路径一并发给用户，引导用户打开链接把截图/视频直接拖进正文或评论区。
3. 确认发布成功后清理 `workspace/.issue-draft.md`。

### 路径 2：未安装或未登录 `gh`（零依赖网页一键提交兜底）

不卡住用户，也不强迫装 `gh`：
1. 生成带 URL 编码参数的预填链接（避免 URL 过长，完整 Markdown 放在代码块方便一键复制）：
   - 新建 Bug：`https://github.com/modelzen/vonvon-bot/issues/new?template=bug.yml&title=<URL编码标题>&version=<版本>&environment=<环境>`
   - 新建功能建议：`https://github.com/modelzen/vonvon-bot/issues/new?template=feature.yml&title=<URL编码标题>`
   - 补充已有 Issue：`https://github.com/modelzen/vonvon-bot/issues/<编号>`
2. 附上排版整洁、可直接复制的文本块和已脱敏媒体路径，并提示：若以后经常反馈，随时可以说「帮我升到 B 档装一下 `gh`」。

## 第六步：简洁收尾与后续引导

发布完成并交回链接后，用 1 句话做清晰收尾：
> 「已发布完成，你可以点上面的链接随时跟进维护者回复。如果后续还有新的报错线索，或者有别的问题想查，直接发这里就行。」（如用户主动询问如何自己提交代码修复，友好指路查看 `modelzen/vonvon-bot` 的 `CONTRIBUTING.md`。）
